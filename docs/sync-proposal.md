# Windows 收藏存储与增量同步

2026-10-29 实现并部署。设置、播放队列和播放进度仍只在本机保存。

## 收藏模型

- 自建歌单同时容纳歌曲和子歌单，共用一条有序条目序列；没有文件夹类型和动态引用。
- 每个子歌单恰有一个父级，支持最多 64 层，不允许循环。根级使用内部根容器。
- 删除歌单按提交时的当前树递归删除子树。先移出的子歌单保留，先移入的子歌单一起删除。
- 歌曲身份为 BVID＋CID。同一歌单不能重复收录同一音源；不同歌单可各自收录。
- 收录关系属于歌单与音源，不属于设备。取消收录按歌单＋BVID＋CID 执行。
- 播放全部深度优先展开当前顺序，重复音源保留第一次出现的位置。队列保存独立快照。

“我喜欢”是固定的系统歌单：固定入口、不可删除或移动、不能包含子歌单、不能手动排序。
按设备记录的收藏时间倒序；相同时间按服务端确认顺序倒序，未确认时暂用本机顺序。
重复添加保留原记录和时间；移除后重新添加产生新的收藏时间。取消喜欢不影响其他歌单。
云端 `received_at` 是独立的接收时间，不能当作设备发生时间。迁移前记录的接收时间未知，保留 NULL。

## 物理存储

本机 `library/library.db` 使用 Microsoft.Data.Sqlite、WAL、FULL synchronous 和外键约束。

| 本机表 | 一行表示什么 |
| --- | --- |
| `profiles` | 一个账号或未登录库的基线版本、摘要、待同步流身份、下一序号 |
| `media` | 一个音源及标题、封面、作者、时长 |
| `playlists` | 一个系统或自建歌单 |
| `playlist_items` | 一条歌曲收录或子歌单关系、排序键、收藏时间 |
| `pending_operations` | 一个有稳定 ID 和连续序号的待提交操作 |

关系表的 `layer` 区分 `base` 和 `work`：云端已确认基线与叠加本机操作后的工作视图。
账号间按 `profile` 隔离。基线、工作关系、同步游标和操作队列在同一 SQLite 事务中保存。
写入按差异更新关系行，不重写整个收藏文档。读取和纯模型运算仍使用内存投影，规模很大时有 O(N) 读取／摘要开销。

云端对应 `music_media`、`music_playlists`、`music_playlist_items`；另有：

| 云端表 | 用途 |
| --- | --- |
| `music_sync_state` | 当前 revision、摘要和最早可增量恢复的游标 |
| `music_sync_changes` | 已确认的实际关系变更及前后摘要，供短期增量拉取 |
| `music_sync_writers` | 待同步操作流的已确认序号上限，供幂等重试 |

`writer_id` 是同步流的随机标识，与条目所有权无关，不存储在歌曲收录关系中。
每个流保留一条高水位记录，避免为百万次操作永久保留百万条回执。
客户端严格按连续序号提交，不跳过无效操作；服务端对无效业务目标确认 no-op 后推进高水位。

JSON 用于请求／响应、快照和单个操作载荷；没有整库 JSON 业务列。
UUID、整数、时间有明确类型；标题和 URL 是变长文本，行长度不固定。
歌曲数和子歌单数可从父级索引上的关系计算；递归展开歌曲数会去重，不能简单加总子歌单数量。

## 排序键

使用 [rocicorp fractional-indexing 3.2.0](https://github.com/rocicorp/fractional-indexing/tree/v3.2.0) 的变长字符串键，
C# 与 SQL 实现一致，使用 ordinal／PostgreSQL `COLLATE "C"` 排序。

插入时在左右相邻键之间生成新键。头尾插入使用可变长度整数部分，普通插入或移动只改变当前关系行，
不用更新后面一百万项的序号。测试覆盖连续一百万次头部插入。

操作保存“X 在 Y 前／后”的意图，服务端在当前顺序上分配最终键；锚点消失时安全跳过。
若极端密集地反复插入同一缝隙，键长超过 256 时重新分配该父级的键并记录实际变更。
这类维护有 O(N) 开销，不宣称永远无需重排。

## 提交与重放

1. 用户操作先在本机持久化并显示，不等待网络。
2. 后台从基线 revision／hash 拉取增量或快照，校验内容并推进基线。
3. 在后台重放全部未确认操作，发布前检查是否有新操作追加，有则包含新尾部重新计算。
4. 提交至多 128 个连续操作及基线 revision／hash；大批次还按载荷大小切分。
5. 服务端按账户取得事务锁，检查基线；过期则只返回最新状态，客户端重放后再提交。
6. 服务端按序应用操作、记录实际变更、推进 revision 和流高水位，在同一事务中完成。
7. 客户端只移除已确认序号及之前的操作，原子保存新基线、剩余队列和工作视图。

同一账户只有一个本机同步流程在途。HTTP 等待和重放计算不持有本机编辑锁；本机事务短暂串行执行。
账号切换使旧请求失效，旧响应不能覆盖新账号。
创建／添加目标被删除、循环移动或丢失排序锚点是 no-op；网络、登录和系统错误保留队列并重试。
每个已接受操作（包括 no-op）都推进服务端 revision，客户端不靠时间戳决定提交先后。

停止编辑 400ms 后安排同步；持续编辑时，从最早未提交操作起最多等待 2 秒安排一批。
单调时钟计算期限。2 秒是调度目标，不是发送／成功时限；断网、挂起、已有在途请求、队列积压都可能延后。
登录、手动同步、恢复前台、网络恢复也会触发检查；另每 30 秒检查远端状态。
恢复前台／网络事件使用 15 秒缓存期限。打开收藏页或切换歌单不触发请求。
无变化时只返回 revision／hash／确认游标，不上传空操作批次。

不合并或抵消待提交的“添加→取消”，保持本机意图顺序：

- B 先添加 a 并提交；A 的添加和取消还在本机队列。
- A 随后提交：重复添加无变化，取消仍按歌单＋音源执行。
- 服务端顺序 B+ → A+ → A−，最终 a 不存在。

删除歌单与添加歌曲同理：先添加后删除，或先删除再对缺失目标添加，最终都删除。
本机可用性优先，离线时各端可以不同；恢复同步后按服务器提交顺序收敛。

## 长历史与传输量

当前关系表始终是最终状态。日志只保留每账户最近最多 512 条变更，并受 8MiB 展开内容预算约束。
旧客户端不必重放所有历史：游标过旧、链不连续、摘要不匹配时直接取得当前快照。
增量至多包含 128 条、变更内容低于 512KiB；较大增量会与当前快照比较，选择较省的方式。
大小按展开后的 JSON 文本计算，避免 TOAST 压缩让传输预算失真。

百万次历史最终只剩少量条目时，下载当前快照即可；不下载百万次事件。
快照／增量在账户事务锁下与固定 revision 对应。当前未做大库快照分页。
删除日志可随保留窗口清理，但流高水位保留，响应丢失的旧请求不能因日志清理而再次执行。
协议没有 Realtime 订阅，当前靠轮询和前台／网络事件发现别端修改。

## 基线完整性与授权

`LibraryProtocol.Hash` 对关系行按 UUID 排序，使用明确的 UTF-8、Base64 文本、整数和毫秒时间编码后 SHA-256。
SQL 与 C# 通过同一测试快照核对摘要；不依赖不同 JSON 序列化器生成相同字节。

启动时重算基线摘要，工作视图从基线＋操作队列重建，不相信磁盘上被单独改过的工作行。
基线损坏时先保存 SQLite 备份，保留待提交操作，再获取云端快照。
联网时服务器核对基线 revision／hash，不接受客户端整库覆盖。
没有实现服务端签名：用户同时修改离线基线及本机摘要不能仅靠 SHA-256 检出。
用户也可以修改客户端或通过自己的凭据提交合法操作，缓存校验不能替代服务端授权。

所有公开表启用 RLS，客户端只可 SELECT 自己的行。写入只能走公开 invoker RPC → 私有 definer 命令，
命令从 `auth.uid()` 推导账号并独立验证约束。客户端没有内部修改函数的执行权，没有 service_role 密钥。

## 一次性开发数据转换与验证

当前开发数据只有 3 条默认收藏，没有旧歌单或引用。迁移把音源和收藏关系直接转入新表，
核对 BVID、CID 和收藏时间；旧表及本机 JSON 只作为备份保留，不继续同步、不支持旧客户端。
不提供旧引用展开或长期旧格式兼容。

- `windows.Tests/LibraryTests.cs`：排序、混排、递归删除、ABA、SQLite 原子写入、重启、基线损坏恢复、
  多副本、丢失回包、网络中继续编辑和账号切换。
- `windows/Tools/LibraryDbTests`：PGlite 实际 PostgreSQL 测试，含 SQL／C# 公共摘要快照、日志裁剪与 RLS。
- `supabase/tests/music_library.sql`：真实 Supabase 事务内回归，最后 ROLLBACK，不留测试账号或发信。
- Debug 隔离样例验证混排／展开界面，不改真实账号的收藏。
