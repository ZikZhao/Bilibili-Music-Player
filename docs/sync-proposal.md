# 收藏同步方案（讨论稿，尚未实施）

本文件描述下一版的目标；当前生产代码仍是整份 JSON 收藏文档、整库 revision 校验和显式冲突处理。
本轮没有更改 Supabase 表、RPC、账户数据或现有引用关系。

## 已明确的交互规则

- 统一“文件夹”和“歌单”：歌单是可同时包含歌曲和子歌单的容器。
- 移除歌单动态引用，每个子歌单只有一个父级，所有歌单形成树。同一首歌可加入多个歌单。
- 删除父歌单时递归删除整棵子树及其中的歌曲条目，不把子歌单提升到上一级；其他歌单中的同一首歌不受影响。
- 操作在本机立即生效并持久化，云端同步在后台批量进行，不按页面访问触发整库下载。
- 先按云端版本推进本地基线，再重放待提交操作。目标已被删除等导致操作无法重放时，跳过该操作，不弹冲突错误、不无限重试，不自动复活歌单。
- 设置继续仅在本机持久化，不进入收藏协议。

## 方案比较

1. 整库快照＋revision：当前实现。保证旧快照不能覆盖新快照，但冲突范围大，传输完整元数据。
2. 每个歌单分别校验：减少冲突范围和传输量，跨歌单移动及嵌套删除仍需要事务协调。
3. 基线＋持久化操作队列＋服务端变更日志：建议的下一版。离线操作可重放，拉取按版本增量；代价是操作定义、重放、去重和日志保留机制。

即时本地编辑和离线期间多端始终完全一致无法同时保证。界面显示本机工作视图；
服务端已提交状态是基线，待同步操作单独保存。目标是恢复网络后收敛，以及崩溃和重试安全。

## 数据关系

| 数据 | 内容 |
| --- | --- |
| 歌单 | 稳定 UUID、所属用户、名称、删除标记等 |
| 条目 | 稳定 UUID、父歌单、类型（歌曲／子歌单）、对应目标、排序键、删除标记 |
| 歌曲元数据 | 稳定 UUID、BVID＋CID、标题、封面、作者和时长等 |
| 已提交变更 | 账户内单调版本号、操作 ID、服务端确认后的实际变更 |
| 操作回执 | 操作 ID、结果及对应版本，用于响应丢失后的幂等重试 |

歌曲收录关系属于“账户下的歌单＋音源”，不属于设备，也不记录哪台设备拥有该条目。
默认收藏夹同一音源仅有一条有效收录关系；重复添加由服务端归并为同一关系，取消即移除该关系。
请求操作 ID 是传输去重信息，不能成为按设备分别保留收藏副本或限制删除的依据。

父子关系由子歌单条目表达，不再额外维护一套独立的可写 parent_id，避免两个事实来源。
同一子歌单最多存在一个有效父子条目，歌曲条目可以出现在不同歌单中。
服务端检查同一用户、目标存在、单父级、禁止循环、根容器不可移动等约束。
歌曲和子歌单共用一条有序条目序列，支持混合排序。

直接歌曲数、直接子歌单数和递归展开歌曲数是不同指标。从关系中计算并在本机维护派生缓存；
递归去重数量不能直接加总子歌单计数。若增加服务端计数字段，应与条目变更同事务维护，不能由客户端单独上报。

## 同步流程

1. 本机原子保存工作状态和操作队列。不能只更新界面或收藏文件，而把待上传操作留在内存。
2. 后台拉取 `base_revision` 之后的已提交变更，按服务端版本顺序更新基线。
3. 从新基线按本机操作顺序重放待提交操作，重建工作视图；已失效的操作作为已处理的 no-op 移出待提交队列。
4. 提交剩余操作，携带基线版本和稳定的操作 ID。
5. 服务端在同一短事务内取得账户级写入锁、检查基线版本、去重、验证并应用操作、保存回执和变更日志、推进版本。
6. 若基线已经过期，返回“需要重放”和新的版本／变更，不应用这批旧基线上的操作。客户端再次执行拉取和重放，不显示业务冲突错误。
7. 接收服务端实际变更和回执，原子推进本地基线、确认操作并重放剩余队列。自己的已确认操作不能再次叠加到工作视图。

客户端时间戳只用于显示。提交顺序来自账户级锁保护的递增版本，不能用客户端时间比较新旧，
也不能假设普通数据库序列的分配顺序等于事务提交顺序。操作 ID 负责幂等，不负责时间排序。
锁只持有到本次短事务完成，不跨网络请求或等待用户。

业务约束失效才是 no-op。超时、断网、登录失效和未识别的服务端错误不能当成“成功跳过”；
这些情况保留队列，稍后重试或等待登录。一次添加多首歌曲等用户原子操作，其条目、计数及日志必须一起提交。

## 删除与添加的两个顺序

共同基线为 v42：A 删除歌单 P，B 向 P 添加歌曲。

- A 先提交：云端 v43 删除 P。B 拉取 v43 后重放添加，目标不存在，跳过；最终两端均不显示 P，不报冲突错误。
- B 先提交：云端 v43 添加歌曲。A 拉取后重放删除并提交 v44；B 拉取 v44 后删除 P。最终相同。
- 拉取和提交之间再次发生远端变更：提交事务中的版本检查拒绝旧基线，客户端继续拉取／重放。
- 提交成功但响应丢失：沿用同一操作 ID 重试，服务端返回原回执，不能重复添加条目或创建歌单。

删除需要可同步的删除记录。旧设备离线超过日志保留期时取得完整快照，再重放本机队列；
旧 ID 不得被普通添加操作隐式重建。回执及删除记录的清理必须与支持的离线窗口、设备确认版本和快照恢复一起设计。

## 递归删除与并发移动

删除命令指定父歌单 ID，在重放后的当前树上计算整棵子树，不携带客户端旧视图中固定的后代名单。
服务端将实际删除的歌单及条目、相关计数和删除日志在同一事务内提交；已提交变更记录实际影响的 ID。

- 子歌单先成功移出待删子树：后续重放删除时它已不在子树中，保留。
- 子歌单先成功移入待删子树：后续重放删除时包含它，一并删除。
- 父歌单先删除：随后向其中添加、从其中移出已删除的子歌单，或移入该父级的操作无法重放，按无效操作跳过，不复活节点。
- 歌曲元数据可被其他歌单共享。删除子树移除其中的歌曲条目，不删除其他歌单中的成员关系。

## 排序和增量

本机操作表达意图，例如“将条目 X 移至 Y 后面”，使用稳定条目 ID，不把旧数组下标当作最终顺序。
服务端在当前有效顺序上计算排序键。已提交日志携带最终条目变更及排序键；
重排排序键等维护操作也必须包含在增量内，使各端得到一致的基线。
同一条目上的并发改名或移动可依服务端提交顺序生效；目标不存在或形成循环的操作无法重放时跳过。

增量同步仍保留完整快照兜底：首次登录、换设备和日志过期时下载快照，正常同步只传变更。
Realtime 如采用，仅通知“有新版本”，不作为可恢复的持久日志；重连后仍以版本游标补齐。

## 长历史、检查点和日志压缩

版本号是同步游标，不代表客户端需要重放的次数。服务端始终保存当前有效收藏状态，
不依赖从第一条历史事件开始重建收藏。协议按以下方式选择传输内容：

- 客户端落后较少且仍在日志保留窗口内：返回有固定截止版本的增量。
- 可将同一对象的已提交历史压缩为该截止版本下的最终状态，以及必须保留的删除信息。
  客户端原子应用整批状态补丁，不能在逐条应用的中间阶段发布悬空父子关系。
- 客户端落后太多、日志已清理，或预计增量负担大于当前快照：返回当前状态快照及其版本，
  再重放本机尚未确认的操作。不要求客户端下载被压缩或清理的原始历史。
- 例如历史已有一百万次修改、当前仅一千个有效条目：可传一千个条目的当前快照，
  不传一百万条历史。传输量不保证恰好等于净新增的一个条目，但受当前状态规模约束。

快照内容和版本号必须来自同一个一致视图；分页时固定快照版本及内容，不能每页读取
不同的新状态再标记成同一版本。增量同样需要固定截止版本及完整范围，不能漏掉同时发生的提交。
可通过单语句一致读取、正确的事务快照或不可变的物化快照提供该保证。
参考：[PostgreSQL 事务隔离与快照](https://www.postgresql.org/docs/17/transaction-iso.html)。

服务端维护检查点和最早可增量同步版本，按容量／保留窗口清理日志，版本号继续递增而不重置。
过老设备切换为快照同步，不因一个长期离线设备无限保留全部历史。
清理历史、删除标记与操作去重信息不是同一件事；必须保留安全的幂等判重能力，
例如操作回执或经过完整协议设计的请求去重检查点，防止旧请求在日志清理后再次执行。
客户端取得快照时也必须确认待提交操作是否曾被服务端接受，避免响应丢失后重复重放。

压缩对象是已提交的云端历史，本机待提交操作保留意图及依赖顺序。
未发送且没有其他依赖的连续改名可合并。不能笼统地抵消“添加后删除”：按歌曲去重的收藏关系
可能被另一端同时添加，丢掉取消操作会改变结果。只有从未发布、ID 仅本机可知的新对象，且
其创建和删除不影响任何既有对象或后续依赖时，才可能证明这组操作可以安全抵消。
已发出但结果未知的操作不能随意改写 ID 或删除，需先取得回执或用同一 ID 幂等确认。
不把本机最终快照直接覆盖云端来代替重放，以免抹掉另一端的有效修改。

## 同步期间继续编辑

不因正在同步而禁用收藏编辑，不在网络等待期间持有本机编辑锁。
每轮同步截取一个固定的待提交批次，用户随后新增的操作立即持久化并加入队尾；
本地视图随操作更新，不等本轮网络请求完成。上传可以防抖合并，但应有最长等待时间，
避免持续编辑导致同步永远不能开始。

回包只确认响应中明确列出的操作 ID，不能清空整个队列。
在新基线上重放所有仍未确认的操作，包括请求发出后新增的操作，再一次性发布工作视图，
防止回包使界面跳回旧状态、暂时复活已删除歌单，或把后来的修改错误标为已同步。

下载、解析和较大的重放计算在后台完成。本机基线、队列确认和工作视图的提交必须原子进行，
这个本机提交阶段可以短暂串行化，但不得跨网络等待。后台计算期间若有新的编辑，
发布前通过编辑代数检查并重放新增尾部操作，不能直接安装过期的计算结果。
账户切换后，旧账户的响应不得应用到新账户。

现有实现也把 HTTP 读写放在本机 `_gate` 之外，并用 `_editVersion` 保留上传期间的新编辑；
它尚无上述操作队列、增量、快照切换和日志压缩协议，不能将这些设计描述为当前已实现。

## 迁移前仍需明确

- 一首歌曲在展开多个子歌单时是否去重，以及对应数量的展示口径。
- 已有引用如何物化为普通歌曲条目或独立子歌单副本，不能直接移除引用记录而丢失用户可见内容。
- 排序锚点失效后的降级位置、日志／回执保留窗口，以及本机原子持久化实现。

## 基线完整性与信任边界

当前 JSON 文件只检查格式、账户归属和图约束，没有服务端签名。手工修改后仍满足结构约束的
内容可能被正常读取；不能把“通过结构校验”描述为“证明是服务器签发的基线”。

新协议的基线表示“服务器在某个版本接受的状态”，与用户编辑后的工作视图区分保存。
基线版本并不代表已经最新；离线期间它可以是一个有效但过期的版本。

- 基线绑定用户、协议版本、服务端 revision 与内容摘要；增量绑定起止版本及起止摘要，
  应用后验证新基线摘要，再与待提交队列一起原子保存。
- 单独把 SHA-256 与 JSON 放在同一可写文件中只能检出损坏，不能防止用户同时修改内容和摘要。
  联网可向服务器核对该版本的摘要；如要求未改造客户端离线检出伪造基线，需使用服务端签名
  和客户端公钥验证，私钥仅存在服务端。
- 签名和摘要使用明确的确定性编码或保留的签发原文，不能混用不同 JSON 序列化结果。
  基线校验失败时重新取得服务器快照，不将被修改的工作状态当作可信基线上传覆盖。
- 离线换回一份旧的有效签名快照属于回滚，仍需联网版本校验；签名不证明缓存已经最新。
- 用户能够改磁盘、待提交操作乃至客户端程序。无法保证被修改的程序仍执行检测，也无法
  区分一个本来就有权限的合法 API 操作是否来自鼠标点击。客户端缓存不是云端授权依据。
- 服务端只根据认证身份与自己的当前数据验证操作，检查所属账户、树约束、固定默认歌单、
  条目唯一性、排序及计数等规则；不接受客户端提供的 owner、计数或完整基线作为可信事实。

参考：[CWE-602：不能仅依赖客户端实施服务端安全规则](https://cwe.mitre.org/data/definitions/602.html)、
[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)。

## 提交节奏和重复收藏的语义

传输可以合并，但操作含义与既定服务端提交顺序不能因批处理改变。
新版拟定初始参数：停止编辑 400ms 后安排提交，连续编辑时最迟每 2 秒安排一批；
这是安排后台请求的时机，不是网络成功提交的时限。有请求在途时保留后续队列，结束后续传。
参数在实现后根据请求耗时验证；
断网重连、恢复前台、账户登录及用户手动同步也触发同步。进入页面读取本机视图，
不把每次访问页面都当作一次强制整库同步。

对默认收藏夹，建议按音源键（BVID＋CID）去重，而不是每台设备创建一条互不关联的重复记录。
如果按“取消该歌单对此音源的收录”定义取消操作：

1. A 添加 a，等待服务端确认；
2. B 添加同一音源 a，服务端确认（建议已有时无变化）；
3. A 取消 a，等待服务端确认；

则最终 a 不在默认收藏夹。每个操作都已依次确认的前提下，立即发送和批量传输不能给出不同结果。
如果 A 的添加和取消从未上传，B 已经成功收藏了 a，就不能删除 A 的两条待提交操作来“优化”，
否则可能保留 B 的收藏，而完整执行取消会移除它。
没有上述提交先后前提时，网络批处理可能改变不同设备操作的交错顺序；最终结果按实际提交顺序决定。

用户已选择按“歌单＋音源”取消收录，不区分由哪台设备添加。
取消命令使用歌单及稳定音源键（BVID＋CID），不能只携带本机临时入列 ID 而误保留另一端的同曲记录。
客户端重放、服务端提交和日志压缩使用相同定义。
与之不同，移除子歌单仍按子歌单身份及其当前树结构处理。

现有运行版仍在本机修改保存后使用 700ms 防抖，同时会在登录、进入收藏页及切换收藏夹时尝试同步；
上述 400ms／2 秒及按操作提交属于新版设计，尚未替换运行版同步逻辑。

## 默认收藏夹：固定的歌曲时间线

- 系统为每个账户保留一个默认收藏夹，使用稳定身份／类型识别，不依赖可变的显示名称。
- 默认收藏夹的入口位置固定，不可移动到其他父级或调整其顺序；歌单本体保留。
- 仅能放歌曲，不能新建、移动或引用子歌单进入其中。
- 歌曲固定按收藏时间倒序，最新添加在顶部；不提供手动拖动、标题排序等替代顺序。
- 允许移除歌曲，不影响其他自建歌单中的同一音源。用户可另外建立“最喜爱”等普通歌单。
- 同一音源已收藏时再次添加为无变化，保留原记录和收藏时间；移除后重新收藏才记录新的
  设备发生时间并进入新时间点。不能因为别的设备重复提交就刷新原时间。
- 使用设备记录的收藏发生时间排序，离线操作同步后仍保留该时间，不用云端收到的时间替换。
  相同时间以稳定的收录顺序裁决：新版用服务端确认顺序，未同步时暂用本机操作顺序。
- 设备报告的发生时间不等于经验证的真实时间；服务端接收时间另存，不能混淆两者的可信程度。
